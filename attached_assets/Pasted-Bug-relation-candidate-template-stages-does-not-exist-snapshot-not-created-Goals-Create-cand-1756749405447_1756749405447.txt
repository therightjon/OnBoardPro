Bug: relation "candidate_template_stages" does not exist + snapshot not created

Goals
- Create candidate_template_stages (idempotent).
- Backfill snapshot rows for existing candidates (best effort from current template_stages).
- Stamp candidate_tasks.stage_order_index for fast sorting.
- Update expand_template to always write the snapshot.
- Make API handlers resilient if snapshot is temporarily empty.

DB migration (Postgres 16, idempotent)

-- A) Table + indexes
DO $$
BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM information_schema.tables WHERE table_name = 'candidate_template_stages'
  ) THEN
    CREATE TABLE candidate_template_stages (
      id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
      candidate_id uuid NOT NULL REFERENCES candidates(id) ON DELETE CASCADE,
      stage_id uuid NOT NULL REFERENCES hiring_stages(id),
      stage_name_snapshot text NOT NULL,
      order_index integer NOT NULL,
      created_at timestamp NOT NULL DEFAULT now(),
      updated_at timestamp NOT NULL DEFAULT now()
    );
    CREATE UNIQUE INDEX uniq_candidate_stage
      ON candidate_template_stages(candidate_id, stage_id);
    CREATE INDEX idx_candidate_stage_order
      ON candidate_template_stages(candidate_id, order_index);
  END IF;
END$$;

-- B) Helper trigger for updated_at (if not already present)
CREATE OR REPLACE FUNCTION set_updated_at() RETURNS trigger AS $$
BEGIN NEW.updated_at = now(); RETURN NEW; END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS trg_candidate_template_stages_updated_at ON candidate_template_stages;
CREATE TRIGGER trg_candidate_template_stages_updated_at
  BEFORE UPDATE ON candidate_template_stages
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();

-- C) Optional column on candidate_tasks for sorting
DO $$
BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM information_schema.columns
    WHERE table_name='candidate_tasks' AND column_name='stage_order_index'
  ) THEN
    ALTER TABLE candidate_tasks ADD COLUMN stage_order_index integer;
  END IF;
END$$;

-- D) Backfill snapshot for existing candidates missing rows
-- (Uses current template_stages as best-effort snapshot)
WITH candidates_needing AS (
  SELECT c.id AS candidate_id, c.template_applied_from_id AS template_id
  FROM candidates c
  WHERE c.template_applied_from_id IS NOT NULL
    AND NOT EXISTS (
      SELECT 1 FROM candidate_template_stages s
      WHERE s.candidate_id = c.id
    )
)
INSERT INTO candidate_template_stages (candidate_id, stage_id, stage_name_snapshot, order_index)
SELECT
  cn.candidate_id,
  ts.stage_id,
  hs.name,
  ts.order_index
FROM candidates_needing cn
JOIN template_stages ts
  ON ts.template_id = cn.template_id AND ts.is_active = TRUE
JOIN hiring_stages hs ON hs.id = ts.stage_id
ORDER BY cn.candidate_id, ts.order_index
ON CONFLICT (candidate_id, stage_id) DO UPDATE
SET stage_name_snapshot = EXCLUDED.stage_name_snapshot,
    order_index         = EXCLUDED.order_index,
    updated_at          = now();

-- E) Backfill stage_order_index on candidate_tasks
UPDATE candidate_tasks ct
SET stage_order_index = s.order_index
FROM candidate_template_stages s
WHERE s.candidate_id = ct.candidate_id
  AND s.stage_id = ct.stage_id
  AND (ct.stage_order_index IS NULL OR ct.stage_order_index <> s.order_index);

-- F) Seed current_stage_id to first snapshot stage if null
DO $$
BEGIN
  UPDATE candidates c
  SET current_stage_id = s.stage_id, updated_at = now()
  FROM LATERAL (
    SELECT stage_id
    FROM candidate_template_stages s
    WHERE s.candidate_id = c.id
    ORDER BY s.order_index ASC
    LIMIT 1
  ) s
  WHERE c.current_stage_id IS NULL
    AND EXISTS (SELECT 1 FROM candidate_template_stages x WHERE x.candidate_id = c.id);
END$$;

Server changes

1) expand_template(template_id, candidate_id)
- After copying template_tasks → candidate_tasks, write the snapshot every time:

WITH ts AS (
  SELECT ts.stage_id, hs.name AS stage_name, ts.order_index
  FROM template_stages ts
  JOIN hiring_stages hs ON hs.id = ts.stage_id
  WHERE ts.template_id = $1 AND ts.is_active = TRUE
  ORDER BY ts.order_index
)
INSERT INTO candidate_template_stages (candidate_id, stage_id, stage_name_snapshot, order_index)
SELECT $2, stage_id, stage_name, order_index FROM ts
ON CONFLICT (candidate_id, stage_id) DO UPDATE
SET stage_name_snapshot = EXCLUDED.stage_name_snapshot,
    order_index         = EXCLUDED.order_index,
    updated_at          = now();

UPDATE candidate_tasks ct
SET stage_order_index = s.order_index
FROM candidate_template_stages s
WHERE s.candidate_id = ct.candidate_id AND s.stage_id = ct.stage_id AND ct.candidate_id = $2;

-- Optional: set current_stage_id to first order_index
UPDATE candidates c
SET current_stage_id = s.stage_id
FROM candidate_template_stages s
WHERE c.id = $2 AND s.candidate_id = $2 AND s.order_index = 1;

2) API resilience
- GET /api/candidates/:id/stages:
  If candidate_template_stages has no rows for this candidate, return [] (do NOT throw).
- GET /api/candidates/:id/tasks:
  Left join stage_order_index; if NULL, compute on the client as a fallback (push those tasks to the end).
- Add logs to warn when a candidate has no snapshot so we can diagnose, but never crash the route.

Frontend
- In /candidates/[id], if stages[] is empty, show a non-blocking banner:
  “Stage sequence not found for this candidate. Using default grouping.”
- Still display tasks grouped by stage name; unknown order groups appear last.
- Once migration/backfill runs, the ordered view takes effect without code changes.

Acceptance
- The error “relation candidate_template_stages does not exist” is gone.
- Previously created candidates now show Tasks by Stage in a stable order (from backfill).
- New candidates always snapshot stage order at creation.
- API routes do not crash if snapshot is temporarily missing; UI degrades gracefully.
