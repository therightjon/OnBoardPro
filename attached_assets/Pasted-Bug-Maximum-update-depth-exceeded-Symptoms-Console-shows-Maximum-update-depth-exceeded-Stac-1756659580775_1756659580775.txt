Bug: Maximum update depth exceeded

Symptoms
- Console shows “Maximum update depth exceeded”.
- Stack mentions: NewCandidateDialog, CandidatesPage, AppLayout, ThemeProvider, ProtectedRoute.

Goal
- Remove all setState loops caused by useEffect without a stable dependency array or navigation/state updates executed on every render.
- Keep the UI behavior unchanged.

Do this exactly:

1) NewCandidateDialog (src/components/new-candidate-dialog.tsx)
- Find any useEffect that calls setState or form.reset and either:
  a) Add a correct dependency array, or
  b) Move the update into an event handler.
- Typical fixes:
  - If we reset the form when the dialog opens, do:
    const [open, setOpen] = useState(false);
    useEffect(() => {
      if (open) form.reset(defaultValues);
    }, [open]); // not on every render

  - If options depend on candidateTypeId, compute with useMemo:
    const filteredTemplates = useMemo(
      () => templates.filter(t => t.candidateTypeId === candidateTypeId),
      [templates, candidateTypeId]
    );

  - If a query should run only when candidateTypeId is set:
    const { data: tmpl } = useQuery({ queryKey: ['templates', candidateTypeId], queryFn: fetcher, enabled: !!candidateTypeId });

  - Never call setOpen inside an effect that depends on open. Remove patterns like:
    useEffect(() => { setOpen(true); }, [open]);

2) ProtectedRoute (src/lib/protected-route.tsx or similar)
- Never push/replace in render. Wrap navigation in a guarded effect:
    const router = useRouter();
    const { status, user } = useSession(); // or your auth

    useEffect(() => {
      if (status === 'loading') return;
      if (!user) {
        router.replace('/login');
      } else if (!allowedRoles.includes(user.role)) {
        router.replace('/unauthorized');
      }
    }, [status, user?.id, user?.role, router]);

- Return a loading state when status === 'loading' so we do not render children yet.

3) ThemeProvider (src/components/layout/theme-provider.tsx)
- Ensure we initialize theme once, not on every render:
    const [theme, setTheme] = useState<'light'|'dark'>(() => {
      if (typeof window === 'undefined') return 'light';
      return (localStorage.getItem('theme') as 'light'|'dark') || 'light';
    });

    useEffect(() => {
      document.documentElement.dataset.theme = theme;
      localStorage.setItem('theme', theme);
    }, [theme]); // include dep array

- Remove any effect without a dependency array that calls setTheme.

4) CandidatesPage (src/pages/candidates/index.tsx)
- If we derive UI state from query data, do not setState during render.
- Pattern:
    const { data } = useQuery({ queryKey: ['candidates'], queryFn: fetchCandidates });
    const rows = useMemo(() => mapToRows(data), [data]);
    // If you must sync component state:
    useEffect(() => { setRows(mapToRows(data)); }, [data]); // not every render

5) General guards across the app
- Search for anti-patterns and fix:
  - useEffect(() => { setState(...); });  → must add deps or remove
  - State setters inside render conditionals
  - router.replace(...) or router.push(...) in render → move to useEffect with stable deps
  - Derived state loops:
      useEffect(() => { setA(b); }, [b]);
      useEffect(() => { setB(a); }, [a]); // breaks; remove or combine

6) Tests and acceptance
- Open New Candidate dialog twice. No warning appears.
- Navigate through ProtectedRoute with:
  - logged out user → redirected once to /login, no loop
  - unauthorized role → redirected once to /unauthorized, no loop
- Toggle theme. No loop and theme persists.
- Candidates list loads without repeated setState warnings.
