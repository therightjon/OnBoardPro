Bug: Candidate template info changes when master Template is edited (snapshot violation)

Context / Expected model
- Candidates are created with a required Template.
- expand_template(template_id, candidate_id) runs once and creates a SNAPSHOT:
  • candidate_tasks: copies of template_tasks at time of expansion
  • candidate_template_stages: per-candidate stage order + names at expansion
  • candidates: stores template_applied_from_id and template_applied_at
- After expansion, master Templates must NOT affect existing candidates.

Symptoms
- Editing a Template (name, stages, or template_tasks) shows up on existing Candidate pages.
- This implies some Candidate UI/API is reading live `templates` / `template_stages` / `template_tasks` instead of the snapshot tables or snapshot columns.

Required: Root-cause investigation checklist
1) Grep for accidental live joins in candidate routes:
   - Search in server/api for `FROM templates` or `JOIN template_` inside any `/api/candidates/*` handlers.
   - Search frontend candidate detail for fetches hitting `/api/templates/*` or using `template_stages` directly.

2) Verify queries used by Candidate pages:
   - Candidate tasks endpoint must select ONLY from `candidate_tasks` and (optionally) join `candidate_template_stages` and lookup tables (users, categories, priorities). It must not join to `template_tasks` or `templates`.
   - Candidate stages endpoint must read from `candidate_template_stages` (snapshot), not `template_stages`.
   - Candidate header “Template Information” must use fields snapshotted on candidate, not live template rows.

Hard fixes (idempotent migrations + code changes)

A) Add explicit snapshot columns on candidates (if missing)
DO $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM information_schema.columns WHERE table_name='candidates' AND column_name='template_name_snapshot') THEN
    ALTER TABLE candidates ADD COLUMN template_name_snapshot text;
  END IF;
  IF NOT EXISTS (SELECT 1 FROM information_schema.columns WHERE table_name='candidates' AND column_name='template_version') THEN
    ALTER TABLE candidates ADD COLUMN template_version integer;
  END IF;
END$$;

COMMENT ON COLUMN candidates.template_name_snapshot IS 'Template name captured at expansion time. Display-only on candidate pages.';
COMMENT ON COLUMN candidates.template_version IS 'Optional immutable version number captured at expansion.';

B) Ensure stage snapshot table exists (if missing)
-- candidate_template_stages(candidate_id, stage_id, stage_name_snapshot, order_index, ...)
-- (we already added earlier; re-run safe checks)

C) Ensure expand_template writes snapshots (transactional)
- After copying template_tasks -> candidate_tasks:
  • Write candidates.template_name_snapshot = templates.name at that moment
  • Optional: store template_version if templates has a version column; otherwise set to 1
  • Insert/UPSERT all stages into candidate_template_stages with stage_name_snapshot + order_index
  • Stamp candidate_tasks.stage_order_index from the snapshot

D) Update Candidate APIs to use snapshots only
- GET /api/candidates/:id → include template_name from candidates.template_name_snapshot (fallback to joined templates.name ONLY if snapshot is null)
- GET /api/candidates/:id/stages → SELECT from candidate_template_stages ORDER BY order_index
- GET /api/candidates/:id/tasks → SELECT from candidate_tasks LEFT JOIN candidate_template_stages (for stage_order_index), NEVER join template_tasks/template_stages

E) Backfill existing candidates (best effort, non-destructive)
-- If template_name_snapshot is null, fill it from the current template name:
UPDATE candidates c
SET template_name_snapshot = t.name
FROM templates t
WHERE c.template_applied_from_id = t.id
  AND c.template_name_snapshot IS NULL;

-- Ensure stage snapshot rows exist for each candidate (insert missing from its template_stages)
WITH cte AS (
  SELECT c.id AS candidate_id, c.template_applied_from_id AS template_id
  FROM candidates c
)
INSERT INTO candidate_template_stages (candidate_id, stage_id, stage_name_snapshot, order_index)
SELECT cte.candidate_id, ts.stage_id, hs.name, ts.order_index
FROM cte
JOIN template_stages ts ON ts.template_id = cte.template_id AND ts.is_active = TRUE
JOIN hiring_stages hs ON hs.id = ts.stage_id
LEFT JOIN candidate_template_stages s ON s.candidate_id = cte.candidate_id AND s.stage_id = ts.stage_id
WHERE s.stage_id IS NULL;

-- Stamp stage_order_index on tasks where missing
UPDATE candidate_tasks ct
SET stage_order_index = s.order_index
FROM candidate_template_stages s
WHERE s.candidate_id = ct.candidate_id AND s.stage_id = ct.stage_id
  AND (ct.stage_order_index IS NULL OR ct.stage_order_index <> s.order_index);

F) Guardrails to prevent future regressions
- Add DB comments (already above) and unit tests:
  • Candidate tasks endpoint must not reference template tables
  • Candidate stages endpoint must not reference template tables
- Add TypeScript types/interfaces that expose only snapshot fields to Candidate UI.
- In code reviews/tests, grep to forbid `template_stages` / `template_tasks` in `/api/candidates/*`.

G) UI fixes
- Candidate Information card:
  • Show “Template: {candidates.template_name_snapshot}”
  • Show “Applied: {template_applied_at}” and a small “Template Locked” badge
- Tasks by Stage:

Acceptance tests
- Create Candidate A from Template T1. Change T1 name, stages, or tasks. Candidate A still displays:
  • Original template_name_snapshot
  • Original stage order and stage names from candidate_template_stages
  • Candidate tasks unchanged
- Create Candidate B after edits; B reflects the new template as expected.
- Candidate APIs do not perform any joins to template tables (verified by code scan / tests).
- Editing master templates never alters existing candidate views.
