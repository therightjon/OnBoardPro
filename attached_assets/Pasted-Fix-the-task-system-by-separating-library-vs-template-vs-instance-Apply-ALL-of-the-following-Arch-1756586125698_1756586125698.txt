Fix the task system by separating library vs template vs instance. Apply ALL of the following.

Architecture invariants
1) Task Definitions = library only
   - Table: task_definitions(id, name, description, default_priority_id, default_category_id, archived, created_by, created_at, updated_at)
   - No stage, assignee, or due-rule columns here.

2) Template Tasks = template-specific settings
   - Table: template_tasks(id, template_id, task_def_id, stage_id, due_rule_type, due_rule_value, fixed_date, default_assignee_id, default_priority, default_category_id)
   - due_rule_type enum: days_before_start | days_after_start | days_before_stage | days_after_stage | fixed_date

3) Candidate Tasks = live instances tied to a person
   - Table: candidate_tasks(id, candidate_id NOT NULL, task_def_id NULL, title, description, stage_id, assignee_id, priority, category_id, due_at, status, completed_at, notes, required, created_at, updated_at, archived BOOLEAN DEFAULT false)

API changes
- Remove any endpoint that creates Candidate Tasks from the Templates pages.
- Endpoints:
  - GET  /api/task-definitions
  - POST /api/task-definitions         // create library item only
  - PATCH/DELETE /api/task-definitions/:id  // archive, edit
  - GET  /api/templates/:id/template-tasks
  - POST /api/templates/:id/template-tasks  // adds a Template Task to a template using a task_def_id and due rules
  - PATCH/DELETE /api/template-tasks/:id
  - GET  /api/tasks                     // list Candidate Tasks with filters
  - POST /api/tasks                     // create Candidate Task INSTANCE ONLY
      Required body: { candidate_id, title OR task_def_id, stage_id, priority, category_id, assignee_id, due_at, notes?, required? }
      Optional: save_as_definition: boolean
      Behavior:
        - If save_as_definition = true, also create task_definitions(name=title, description, default_priority_id, default_category_id) and set task_def_id on the new candidate task.
  - GET/PATCH/DELETE /api/tasks/:id     // delete is soft delete (archived=true)

Validation rules
- POST /api/tasks MUST reject when candidate_id is missing. Return 400 with message "candidate_id is required".
- Task Definitions endpoint MUST NOT accept stage, due rules, or assignee.
- Template Tasks endpoint MUST require template_id and task_def_id. It sets stage and due rules there.

Routing and UI
- Sidebar: Dashboard, Candidates, Tasks, My Tasks, Templates, Analytics, Settings.
- /templates
  - Show list of templates. Keep a “Task Definitions” button that navigates to /templates/task-definitions.
  - Do NOT show “New Task” on any Templates screen.
- /templates/[templateId]
  - “Add Template Task” opens a modal:
      fields: task_def_id (select from library), stage_id, due_rule_type, due_rule_value or fixed_date, default_priority, default_assignee_id, default_category_id.
  - No ability here to create Candidate Tasks.
- /templates/task-definitions
  - CRUD for library items: name, description, default_priority, default_category. No stage or due rules.
- /tasks
  - Title: “Tasks”
  - Tabs: All Tasks (default), My Tasks.
  - Columns: Title, Candidate, Stage, Assignee, Priority, Category, Due, Status, Updated, Actions.
  - Filters: assignee, department, division, stage, status, priority, category, due range, overdue.
  - “New Task” opens a modal for Candidate Task creation:
      required: candidate_id
      choose: existing task_def_id OR enter title/description
      other fields: stage_id, priority, category_id, assignee_id, due_at, required
      optional: checkbox “Save as new Task Definition”
- /tasks/mine
  - Same component as /tasks but permanently filtered to assignee_id = current_user.

Server guards
- Department/division scoping based on the candidate’s department/division for department_admin, division_leader, manager.
- Candidates can only see and update their own candidate_tasks.
- HR and System Admin can manage Task Definitions and Template Tasks.

Migrations to apply (idempotent)
- Ensure candidate_tasks has candidate_id NOT NULL FK to candidates(id).
- Ensure task_definitions has NO stage_id, NO due_rule_type, NO due_rule_value, NO default_assignee_id.
- Ensure template_tasks has the due-rule and stage fields listed above.
- Add archived BOOLEAN DEFAULT false on candidate_tasks; DELETE becomes archived=true.
- Add index on candidate_tasks(assignee_id) WHERE status <> 'done' AND archived = false.
- Add index on candidate_tasks(candidate_id, status, due_at) for dashboard queries.

Frontend wiring (TanStack Query keys)
- ['tasks', params], ['tasks', 'mine', params], ['task', id]
- ['task-defs'], ['task-defs', id]
- ['templates'], ['templates', id], ['template-tasks', templateId]

Acceptance checks
- Creating a Candidate Task without candidate_id returns 400 and does not write.
- /templates/[templateId] only creates Template Tasks; it cannot create Candidate Tasks.
- /templates/task-definitions cannot set stage or due rules.
- /tasks can create an instance task, and optionally save its title/description as a new Task Definition.
- /tasks/mine shows only tasks where assignee_id = current_user.
- Editing a Task Definition never changes existing Candidate Tasks.
- Changing a Template affects only future candidates when expand_template runs.
